- 日期：2026-11-14
- 状态：草稿，等待确认

## 1. 这是什么，为什么做

一个 **Alliance Auth（AA）插件**：玩家在 AA 网页上提交工单，选择要找的部门；工单交给对应部门处理，部门收到时由 Discord 在指定频道 @ 指定身份组。部门人员在 AA 里接手、和玩家来回交流，需要时拉其他部门协作或移交上级部门。

为什么做：
- 目前没有现成的 AA 工单插件，联盟内部「找谁办事」靠私聊，容易丢、没记录、没人跟进。
- **开源**，目标是别的联盟 / 军团装上就能用，所以一切都要可配置，并且在 AA **前台**配置，不要求管理员改代码或进 Django 后台。

成功的样子：
- 玩家提交后，对应部门很快在 Discord 收到提醒；没人接手会再提醒、再升级。
- 每张工单都有完整记录，谁接的、说了什么、何时关闭，一目了然。
- 别的联盟按 README 照做就能装好，并能通过 [aa-app-checklist](https://github.com/fthomas-de/aa-app-checklist) 的审查。

## 2. 目标、非目标、反目标

### 目标
1. 玩家提交工单：选部门、分类、紧急程度，写标题和内容，可附图片。【已定】
2. 工单定向到部门，Discord webhook 在该部门的频道 @ 该部门的身份组。【已定】
3. 部门人员「接手」后与玩家在 AA 里来回回复；玩家可以继续补充材料。【已定】
4. 多部门协作（邀请其他部门加入）、移交上级部门、玩家申请上级介入。【已定】
5. 关闭：长时间无人回复自动关闭（关闭前提醒）、管理人员手动关闭、提交人手动关闭。【已定】
6. 上级部门能在 AA 看到下级部门所有工单，但**不会被提醒**。【已定】
7. 紧急程度档位由管理员自己设置。【已定】
8. 超时没人接手再提醒、每个部门自己的问题分类、常用回复模板、统计页面。【已定】
9. Discord 机器人（aa-discordbot）私信：提醒玩家有新回复；玩家能自己关掉；也私信工作人员。【已定】
10. 多语言：英文、简体中文、德语、俄语、西班牙语。【已定】
11. 所有配置在 AA 前台完成。【已定】

### 非目标（这一版不做）
- 在 Discord 里点按钮接手 / 回复工单（需要机器人交互，复杂度高，以后再说）。
- 邮件通知。
- 玩家满意度评分。
- 管理员填写的内容（部门名、分类名、回复模板）的多语言版本——这些按管理员输入的原文显示。【建议】
- 对接 SRP、corptools 等其他插件的数据。

### 反目标（做出来但出现这些情况就算失败）
- 敏感工单（例如举报成员）被不该看的人看到；或者提交人看到了内部备注。
- Discord 频道被刷屏（每条回复都发频道、重试刷屏、@everyone）。
- 插件偷偷创建权限组 / 状态 / 定时任务，或卸载后留垃圾（违反检查清单）。
- 工作人员不处理，工单就被「自动关闭」掉，玩家的问题石沉大海。
- 在树莓派上明显拖慢 AA（每次打开任何页面都查一堆数据库）。
- webhook 地址出现在日志或页面上，被人拿去乱发消息。

## 3. 约束

- **AA 版本**：支持 AA `>=5.0,<6`；测试机（树莓派）和正式服都是 **5.4.0**，以此为准测试。依赖写法不能让 `pip install` 顺带升级 AA（检查清单 1.1.3）。
- **Python / Django**：跟 AA 5.x 的要求走（构建者去 PyPI 查 AA 5.0–5.4 依赖的 Django 版本，按检查清单第 2 节命令）。
- **两边都装了 aa-discordbot**，但插件对它是**可选依赖**：用 `apps.is_installed("aadiscordbot")` 判断，没装时私信功能自动关闭，其他照常。
- **检查清单（aa-app-checklist）全部条目**都要满足，重点：
  - 模板继承 `allianceauth/base-bs5.html`，Bootstrap 5 + FontAwesome 6；
  - 有 `MenuItemHook`，菜单徽章不能每页都查库（要缓存）；
  - 权限 `default_permissions = ()`，每个视图都要 `login_required` + 权限检查，改数据只走 POST + CSRF；
  - **不自动创建** 组、状态、权限分配、`PeriodicTask`；定时任务写在 README 里由管理员加到 `local.py` 的 `CELERYBEAT_SCHEDULE`；
  - 迁移里的 `RunPython` 只动本插件自己的表；
  - 无自动更新、无遥测；
  - 用 `get_extension_logger`；日志不写 token、webhook。
- **许可**：MIT。不复制 GPL / AGPL 代码；参考 django-helpdesk（BSD）、aa-discord-announcements 只看思路，自己写。
- **仓库**：公开仓库里不放真实 ID、真实角色名、真实 webhook。
- **提交署名**：用仓库主人的账号；**不写任何 AI 署名**（不加 Co-Authored-By，不提 AI）。
- **硬件**：测试机是树莓派，要轻量：不引入前端打包工具链，不引入新的重量级依赖。

## 4. 做法比较（Approaches）

| 做法 | 说明 | 取舍 | 结论 |
|---|---|---|---|
| A. 标准 AA 插件（服务端渲染 + Celery 任务 + 前台管理页） | 和 aa-srp、aa-structures 同一形态；页面用 AA 自带 Bootstrap 5，少量原生 JS；通知、提醒、自动关闭走 Celery；所有配置在插件自己的「管理」页面 | 最贴合 AA、最容易给别人安装、树莓派压力小；前台管理页要自己写表单 | **采用** |
| B. 同 A，但配置放 Django 后台 `/admin` | 开发省事 | 违背「一切在前台处理」的要求 | 不采用（Django 后台只做备用：见第 11 节） |
| C. 独立前端（React/Vue）+ API | 交互更花哨 | 风格和 AA 不一致，部署复杂，树莓派要打包工具链，违背开源易用 | 不采用 |

需求方没有异议，按 A 做。

## 6. 角色与权限

### 6.1 插件定义的 Django 权限（`default_permissions = ()`）【建议】

| codename | 显示名 | 作用 |
|---|---|---|
| `basic_access` | Can submit and view own tickets | 看到菜单、提交工单、看自己的工单。管理员把它给哪些状态 / 组由管理员决定【已定：用权限控制】 |
| `view_all` | Can view all tickets | 看到所有部门的工单，并拥有和「负责部门的上级部门人员」相同的操作权（回复、内部备注、接手、移交、邀请、关闭），但不收提醒、菜单徽章不计。适合联盟 CEO / 高层，作为部门树之外的兜底 |
| `manage` | Can manage ticket settings | 进入「管理」页：部门、紧急程度、分类、回复模板、全局设置 |

- **部门人员不靠权限，靠部门绑定的 AA 权限组**：一个部门可绑定一个或多个 `Group`，在组里的人就是这个部门的人员。【建议】组由管理员自己建，插件只让你选，不会创建。
- 部门人员要能打开插件页面，也需要 `basic_access`（README 写明：给部门组也加上这个权限，或给所有成员状态加）。
- **超级用户**：`has_perm` 恒为真，所以超级用户等同拥有 `view_all` 和 `manage`；但超级用户**不自动算作任何部门人员**，因此不会被 @、不会收私信，除非他本人在部门组里。README 里写明这一点（检查清单 4.3.1）。

### 6.2 谁能看到一张工单【已定：部门成员和上级都能看】

能看到工单 T 的人：
1. T 的提交人；
2. T 的**当前负责部门**的人员；
3. 被**邀请协作**到 T 的部门的人员；
4. 以上 2、3 中任一部门的**所有祖先部门**（上级、上级的上级……）的人员；
5. 有 `view_all` 权限的人。

谁能看到内部备注：上面 2–5 的人。**提交人永远看不到自己工单的内部备注，即使他本人也是工作人员**（例如 CEO 自己提交工单）。

这个判断要集中在一个函数 / 查询集里（例如 `Ticket.objects.visible_to(user)` 和 `can_view_internal(user, ticket)`），所有列表、详情、附件下载、统计都用它，不能各写各的。

### 6.3 谁能做什么

先定义两类工作人员【建议】：
- **主管方**：负责部门的人员 + 负责部门所有祖先部门的人员 + `view_all`。
- **协作方**：协作部门的人员 + 协作部门的祖先部门人员。

协作方只能**看、回复、写内部备注**；接手、重新分配、邀请、移交、改档位、关闭只有主管方能做。处理人只有在仍是主管方人员时才有这些权限；离开部门后立即失去全部权限，工单自动回到「待接手」。（0.2.0 起）

**提交人兼工作人员**：不能接手、也不能被分配为自己工单的处理人；自己的工单不出现在自己的「待接手」队列和菜单徽章里。其他操作按提交人身份处理。【建议】

下表中「负责部门 / 祖先部门人员」都指主管方。

| 操作 | 谁能做 |
|---|---|
| 提交工单 | 有 `basic_access`，且（如果部门限制了可提交范围）满足该部门的限制 |
| 回复 | 提交人；负责部门 / 协作部门 / 祖先部门人员；`view_all` |
| 写内部备注 | 工作人员（6.2 的 2–5） |
| 接手 | 负责部门的人员（祖先部门人员也可以接手，相当于上级亲自处理）【建议】 |
| 改为别人处理（重新分配） | 负责部门人员、祖先部门人员【建议】 |
| 邀请协作部门 / 移除协作部门 | 负责部门人员、祖先部门人员 |
| 移交到别的部门 | 负责部门人员、祖先部门人员；可以移交给**任意**启用中的部门（不只是上级）【建议】 |
| 申请上级介入 | 提交人；仅当负责部门有上级部门时 |
| 改紧急程度 / 分类 | 工作人员 |
| 关闭 | 提交人、处理人、负责部门 / 祖先部门人员、`view_all`【已定：管理人员手动关闭、提交人手动关闭】 |
| 重新打开 | 提交人（关闭后 N 天内，N 可设置，默认 7）；工作人员任何时候【建议】 |
| 统计页 | 部门人员看本部门及下级部门；`view_all` 看全部 |
| 管理页 | `manage` |

## 7. 工单生命周期

```
            提交
              │
              ▼
        ┌──────────┐  Discord：负责部门频道 + 按档位决定是否 @身份组
        │ 待接手    │  超时未接手 → 再 @ 一次 → 再超时 → 提醒上级部门频道
        └──────────┘
              │ 接手
              ▼
        ┌──────────┐  提交人 ↔ 工作人员来回回复；可传图片
        │ 处理中    │  邀请协作 / 移交 / 申请上级介入（见下）
        └──────────┘
              │ 手动关闭 或 无人回复超时自动关闭（先提醒）
              ▼
        ┌──────────┐
        │ 已关闭    │  记录关闭方式和关闭人；提交人 N 天内可重新打开
        └──────────┘
```

状态只有三个：`open`（待接手）、`in_progress`（处理中）、`closed`（已关闭）。【建议】另外记录 `closed_reason`：`requester` / `staff` / `auto`。

### 7.1 各动作的效果

- **提交**：状态 `open`，负责部门 = 所选部门。通知见第 9 节。
- **接手**：处理人 = 当前用户，状态 → `in_progress`。时间线写一条「X 接手了工单」。
- **邀请协作**：把一个部门加入「协作部门」列表，该部门人员能看、能回复。Discord 在**被邀请部门**的频道发一条消息（按该工单档位决定是否 @）。负责部门和处理人不变。
- **移交**：负责部门 → 目标部门，处理人清空，状态回到 `open`，未接手计时重新开始，Discord 通知目标部门（等同新工单）。移交对话框里有「原部门继续协作」勾选框，**默认勾选**：原负责部门变成协作部门，原处理人还能看到进展。【建议】
- **申请上级介入**（提交人发起）：上级部门本来就能看到工单，所以这一步的作用是**提醒 + 标记**：在上级部门频道发消息 @ 其身份组（不论档位都 @），通知处理人，工单上显示「已申请上级介入：联盟高层」。负责部门和处理人不变，由上级决定是否亲自接手或移交。提交人可以附一句理由。【建议】
  - 逐级往上：第一次申请找负责部门的上级，再申请就找上级的上级，依此类推；到顶以后按钮隐藏。每一层只能申请一次。
  - 移交到新部门后，申请记录清零，从新部门的上级重新算。
  - 需要单独记录每次申请（目标部门、申请人、理由、时间）。
- **关闭**：状态 → `closed`，写关闭方式和关闭人；关闭时可附一条最终回复。
- **重新打开**：状态回到 `in_progress`（有处理人时）或 `open`（没有时），自动关闭计时清零。

### 7.2 自动关闭【已定：双方都没回复一段时间后自动关闭，关闭前提醒】

- **只对「处理中」的工单生效**。「待接手」的工单不会自动关闭——工作人员不处理就关掉会让玩家的问题石沉大海（反目标）。待接手工单靠第 8 节的「超时再提醒 / 升级」解决。【建议】
- 计时起点：最后一条**回复**（不算内部备注和系统事件）的时间。
- **只有最后一条回复是工作人员发的（在等玩家回话）时，才会计时自动关闭。**【建议】如果最后一条是提交人发的（在等工作人员回话），就不会自动关闭，改成到时间提醒处理人（铃铛 + 私信）和负责部门频道（不 @）一次，避免「工作人员不回就被关掉」。
- 全局设置：无回复 **N 天**后自动关闭（默认 7），提前 **M 小时**提醒（默认 24）。
- 提醒对象：提交人和处理人（AA 铃铛 + 私信）。提醒只发一次，状态存数据库，重启不会重发；之后有新回复就清零重来。
- 需要记录「最后一条回复是哪一方」（例如 `last_reply_by_staff` 字段）。

### 7.3 防滥用【建议】

- 每个提交人同时「未关闭」的工单上限（全局设置，默认 5），超出时提示「请先关闭已处理完的工单再提交」。

## 8. 紧急程度与超时提醒

**紧急程度档位（管理员可增删改）**，每一档有：
- 名称、颜色（从 Bootstrap 语义色里选，如 secondary / primary / danger，保证深浅色模式都清楚，并且界面上同时显示文字，不只靠颜色）、排序；
- 新工单是否 @ 部门身份组；
- 未接手提醒：多少分钟没人接手就再提醒负责部门一次（留空 = 不提醒）；
- 升级提醒：多少分钟仍没人接手就提醒**上级部门**频道（留空 = 不升级；没有上级就跳过）。

默认三档（用迁移在**本插件自己的表**里建，管理员可改可删）：

| 档位 | @身份组 | 未接手再提醒 | 升级到上级 |
|---|---|---|---|
| 低 | 否 | 不提醒 | 不升级 |
| 普通 | 是 | 24 小时 | 不升级 |
| 紧急 | 是 | 30 分钟 | 2 小时 |

- 提醒和升级**各只发一次**，发过的标记存数据库（重启不重发）；移交会清零重来。
- 上级部门平时不被提醒【已定】；只有升级提醒和「申请上级介入」才会 @ 上级。
- 删除档位：如果还有工单在用，不能删，只能「停用」（新工单里不再出现）。

## 9. 通知

### 9.1 Discord 频道（webhook）

每个部门配置：
- 一个 webhook 地址；
- 要 @ 的身份组 ID（可以多个，用数字 ID；界面上给出「怎么复制身份组 ID」的说明）；
- 「测试发送」按钮：向该 webhook 发一条测试消息，结果显示在按钮旁。这是第 13 节「页面请求里不做网络请求」的**唯一例外**：只有管理员会点，同步发送，超时 5 秒。

发到频道的事件（只有这些，不会每条回复都发，避免刷屏）：

| 事件 | 发到哪个部门频道 | 是否 @ |
|---|---|---|
| 新工单 | 负责部门 | 看档位 |
| 移交进来 | 目标部门 | 看档位 |
| 被邀请协作 | 被邀请部门 | 看档位 |
| 申请上级介入 | 上级部门 | 是 |
| 未接手再提醒 | 负责部门 | 是 |
| 升级提醒 | 上级部门 | 是 |

消息内容（Discord embed）：工单编号、标题、部门、分类、紧急程度（颜色条）、提交人主角色名、一个打开工单的链接（用 AA 的 `SITE_URL` 拼接）。**默认不带正文**，因为频道里的人不一定都有权看正文（敏感工单）。【建议】

技术要求：
- 身份组 @ 必须写在消息的 `content` 里（embed 里的 @ 不会响），同时设置 `allowed_mentions` 只允许配置的身份组 ID，禁止 `@everyone` / `@here` / 用户 @。玩家写的标题只放进 embed，所以无法触发任何 @。
- webhook 地址校验允许 `discord.com`、`discordapp.com`、`canary.discord.com`、`ptb.discord.com` 下的 `/api/webhooks/...`。
- 发送走 Celery 任务，带超时；失败有限次重试（例如最多 5 次、指数退避），遇到 429 按 `retry_after` 等待；最终失败写**一行**日志说明原因（不含 webhook 地址），并在该部门的管理页显示「⚠️ 最近一次发送失败（时间、原因）」。
- webhook 地址保存后在页面上只显示末尾几位；校验必须是 `https://discord.com/api/webhooks/...` 或 `https://discordapp.com/api/webhooks/...` 格式。
- 部门没配 webhook 时，不发频道消息，管理页提示「未配置 Discord 频道，新工单不会提醒」。

### 9.2 AA 铃铛通知（始终开启）

用 AA 自带的 `allianceauth.notifications.notify`：

| 事件 | 通知谁 |
|---|---|
| 工作人员回复 / 接手 / 移交 / 关闭 / 重新打开 | 提交人 |
| 即将自动关闭 | 提交人、处理人 |
| 提交人回复 / 申请上级介入 | 处理人（没有处理人则不发，由频道提醒兜底） |
| 你被设为处理人（被别人重新分配） | 新处理人 |

### 9.3 Discord 私信（需要 aa-discordbot）【已定】

- 通过 `aadiscordbot.tasks.send_message(user_pk=..., embed=...)` 发送（它的 README 写明支持 `user_id` / `user` / `user_pk`，`embed` 是 py-cord 的 `discord.Embed`）；判断 `apps.is_installed("aadiscordbot")`，没装就跳过。构建者要对照 5.4.0 环境里实际装的 aa-discordbot 版本确认签名，并且**在我们自己的 Celery 任务里调用、包住所有异常**（用户没绑定 Discord 时它可能直接抛错）。
- 发送的事件和对象**与 9.2 完全相同**（铃铛有的，私信也发一份）。
- 每个用户在插件「个人设置」里可以关掉私信，默认打开；管理员可在全局设置里整体关掉私信功能。
- 收不到的情况（没绑定 Discord、不在服务器、关了服务器私信）：不报错、不重试刷屏，写一行 debug/info 日志；铃铛通知照常。
- 私信内容不带正文（理由同 9.1），只有标题、事件、链接。

## 10. 部门、分类、回复模板

### 部门
- 名称、简介（提交页上显示，帮助玩家选对部门）、排序、启用 / 停用。
- 上级部门（可空）。不能形成环（保存时校验）。
- 绑定的 AA 权限组（一个或多个）= 部门人员。
- 可提交范围（可选）：限定哪些 AA 状态 / 组可以向这个部门提交；留空 = 所有有 `basic_access` 的人。用途：例如「内部审计」部门只对成员开放。【建议】
- 「是否接受玩家提交」开关：关掉后只能被移交 / 邀请，不出现在提交页（例如「联盟高层」这种纯上级部门）。【建议】
- Discord：webhook、身份组 ID（见 9.1）。

举例：外交、后勤、人事都以「联盟高层」为上级；联盟高层绑定 CEO 所在组、不接受玩家提交、平时不被提醒。这样 CEO 自然能看到所有工单。

### 分类【已定】
- 属于某个部门；名称、排序、启用 / 停用；
- 可选「填写模板」：玩家选了这个分类后，正文框预填模板文字（例如「角色名：\n损失链接：\n经过：」）。
- 部门没有分类时，提交页不显示分类选择。

### 回复模板【已定】
- 属于某个部门（或「所有部门通用」）；标题、正文。
- 在回复框旁边有「插入模板」下拉，选中后插入到光标处，可以再编辑后发送。
- 谁能维护：有 `manage` 的人管理全部；部门人员可以管理**本部门**的模板。【建议】

## 11. 消息与附件

- 消息类型：回复、内部备注、系统事件（接手、移交、邀请、改档位、关闭、重开……，显示成时间线上的灰色小字）。
- 正文是**纯文本**，保留换行，自动把网址变成链接；不支持 HTML / Markdown，避免 XSS。【建议】
- 发出后不能编辑、不能删除（工单是记录）；超级用户可在 Django 后台删除消息 / 附件处理极端情况（例如误传隐私截图）。Django 后台对消息和附件只开放「查看 + 删除」，其余模型只读。【建议】
- 显示作者的**主角色名 + 头像**；工作人员的消息旁标注所在部门。

### 附件（图片）【已定：只支持图片】
- 允许 png / jpg / gif / webp；用 Pillow 真正打开校验是图片，不只看扩展名。
- 单个文件大小上限（全局设置，默认 5 MB），每条消息最多 5 张。
- **附件不能放在公开的 media 目录直接访问**：文件存到 `MEDIA_ROOT/aa_ticket/…`（随机文件名），通过插件自己的下载视图返回，视图里按 6.2 检查权限（内部备注的附件只给工作人员）。
- 回复和内部备注都可以带图片；提交工单时也可以带。
- 保留期限（全局设置，默认「不自动删除」）：可设置「工单关闭 X 天后删除附件文件」，由定时任务执行，节省树莓派空间。
- AA 默认**没有设置** `MEDIA_ROOT`（Django 默认是空字符串，会写到当前目录）。README 必须写明在 `local.py` 设置 `MEDIA_ROOT`；插件加一个系统检查（`@register()`）：没设置时在 `manage.py check` 里给出警告，并且上传功能自动关闭、页面提示「管理员未配置附件存储」。

## 12. 页面

所有页面继承 `allianceauth/base-bs5.html`，布局遵守仓库主人的风格（内容优先、留白、语义色、深浅色都清楚、按钮用动词、错误提示说清怎么改、空状态给下一步、手机宽度不横向滚动）。

菜单项「工单」：对部门人员显示徽章 = **自己所在部门直接负责**的「待接手」工单数（不含下级部门的、不含自己提交的）；徽章结果缓存（例如 60 秒），不要每次打开 AA 任意页面都查库。上级部门平时不被提醒，所以下级部门的工单不计入徽章，只在工作台「下级部门」标签里列出。【建议】

## 13. 定时任务（Celery）

全部是普通 Celery 任务，**不在代码或迁移里创建 PeriodicTask**；README 给出 `local.py` 里要加的 `CELERYBEAT_SCHEDULE` 片段：

| 任务 | 建议频率 | 做什么 |
|---|---|---|
| `aa_ticket.tasks.check_unclaimed` | 每 5 分钟 | 未接手再提醒、升级提醒 |
| `aa_ticket.tasks.check_auto_close` | 每 15 分钟 | 自动关闭预警、自动关闭 |
| `aa_ticket.tasks.cleanup_attachments` | 每天 | 按保留期限删除附件文件（设置为不删除时什么都不做） |

- 周期任务用 AA 自带的 `QueueOnce` 防止同时跑多个。
- 通知发送（webhook、私信）是单独的小任务，由用户操作触发（`.delay()`），页面请求里不做网络请求。
- 提醒 / 预警是否已发，存在工单记录上（时间戳字段），重启不丢不重发。

## 14. 多语言【已定】

- 所有界面文字用 Django `gettext` 标记，源语言英文。
- 带的翻译：简体中文（`zh_Hans`）、德语（`de`）、俄语（`ru`）、西班牙语（`es`）。中文由开发者保证质量；德 / 俄 / 西为初版，README 注明欢迎母语用户校对。
- 语言跟随 AA 的语言选择（AA 已有语言切换）。AA 自带翻译只覆盖 AA 本身文字，插件的文字由插件自己的 `locale/` 提供。
- 发到 Discord 的消息用 AA 站点默认语言（`LANGUAGE_CODE`）。私信用收件人的语言【建议】——构建者确认能否拿到用户的语言设置，拿不到就用站点默认语言。
- 时间显示：EVE 时间（UTC，和 AA / 游戏一致）+ 相对时间（「3 小时前」）。【建议，请确认】

## 15. 数据模型（概要，字段名由构建者定）

- `Department`：name, description, parent(FK self, null), groups(M2M Group), submit_states(M2M State), submit_groups(M2M Group), accepts_submissions, is_active, order, webhook_url, mention_role_ids, last_webhook_error / at
- `Priority`：name, color, order, mention_on_new, remind_after_minutes, escalate_after_minutes, is_active
- `Category`：department(FK), name, template, order, is_active
- `CannedReply`：department(FK, null = 通用), title, body
- `Ticket`：number（自增显示用）, title, requester(FK User), requester_character(FK EveCharacter，提交时的主角色), department(FK), category(FK, null), priority(FK, PROTECT), status, assignee(FK User, null), collaborating_departments(M2M Department), created_at, claimed_at, closed_at, closed_by, closed_reason, last_reply_at, reminded_at, escalated_at, autoclose_warned_at
- `TicketMessage`：ticket, author(FK User, null = 系统), kind(reply / internal / event), body, event_type + event_data（系统事件用）, created_at
- `Attachment`：message(FK), file, original_name, size, content_type
- `EscalationRequest`（或直接用事件记录）：ticket, to_department, by, reason, created_at
- `UserPreference`：user(OneToOne), discord_dm_enabled
- `TicketSettings`：单例（用 AA 自带的 django-solo），全局设置各项
- 权限挂在一个无表的 `General` 模型上（AA 插件常用写法），`managed = False`、`default_permissions = ()`。

## 16. 安全要点

- 每个视图：`login_required` + `basic_access`（或更高）+ 对象级检查（6.2/6.3），附件下载同样检查。
- 改数据只接受 POST，CSRF 保护；没有 `csrf_exempt`；没有公开视图。
- 查询集级别过滤可见性，避免「改 URL 里的编号就能看别人的工单」。
- 图片校验（Pillow）、随机文件名、限制大小，返回时设置正确的 `Content-Type` 和 `Content-Disposition`，防止上传 HTML 伪装成图片。
- webhook 地址不写日志、页面只显示末尾几位。
- `allowed_mentions` 白名单。
- 并发：「接手」用数据库条件更新（只有当前仍是待接手才成功），两个人同时点只有一个成功，另一个看到「已被 X 接手」。
