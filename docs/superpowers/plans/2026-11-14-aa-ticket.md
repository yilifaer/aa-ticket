# aa-ticket 施工计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal：** 做一个 Alliance Auth 5.x 插件 `aa-ticket`：玩家按部门提交工单，部门在 Discord 收到提醒，在 AA 里接手、回复、协作、移交、升级、关闭；所有配置在 AA 前台完成。

**Architecture：** 标准 AA Django 插件，页面由服务端渲染（Bootstrap 5 模板，加少量原生 JS）。所有改数据的动作集中在 `services.py`；谁能看、谁能做集中在 `access.py`。每个动作都写一条系统事件，事务提交后交给 `notifications.dispatch()`，由它发 AA 铃铛通知，并排队 Celery 任务发 webhook 和私信。周期任务（未接手提醒、自动关闭、附件清理）由管理员在 `local.py` 里配置。

**Tech Stack：** Python 3.10–3.14、Django 5.2（来自 AA 5.4.0）、Alliance Auth `>=5.0,<6`、Celery + `celery_once.QueueOnce`、django-solo、requests、Pillow、可选 aa-discordbot（py-cord）。

**Spec：** `docs/superpowers/specs/2026-11-14-aa-ticket-design.md`（执行者必须同时读 spec，计划里引用的「§x」都指 spec 的章节）

## Global Constraints

- 依赖：`allianceauth>=5.0,<6`、`Pillow>=10`、`requests`；不能写会让 pip 顺带升级 AA 的依赖；`aadiscordbot` 不写进依赖，运行时用 `apps.is_installed("aadiscordbot")` 判断。
- Python `>=3.10`；包名 `aa-ticket`，模块名 `aa_ticket`，版本 `aa_ticket.__version__ = "0.1.0"`，`pyproject.toml` 动态读取。

## Review Focus

1. **提交人本身也是负责部门的人员**（比如 CEO 给自己的部门提交工单）。在详情页、附件下载、通知和私信里，都不能看到内部备注或内部备注里的图片。→ Task 4（`test_requester_who_is_staff_never_sees_internal`）、Task 9（`test_internal_attachment_hidden_from_requester_staff`）。
2. **改 URL 里的编号去访问别人的工单或附件**，应该返回 404，而不是 403。返回 403 会暴露这张工单确实存在。→ Task 10（`test_detail_other_users_ticket_404`）、Task 9（`test_attachment_of_invisible_ticket_404`）。
3. **两个工作人员同时点「接手」**：只有一个成功，另一个看到「已被 X 接手」。→ Task 5（`test_claim_is_atomic`）。
4. **恶意上传**：把 HTML 改名成 `.png`、超过大小上限、像素炸弹（超大尺寸图片）都要被拒绝，并提示怎么改。→ Task 9（`test_rejects_html_named_png`、`test_rejects_oversize`、`test_rejects_decompression_bomb`）。
5. **还有工单在用时停用部门、删除档位，或把人员移出部门组**：工单不能消失，也不能报 500；删除被拒绝，只能停用；被移出组的人立即失去访问权限。→ Task 3（`test_priority_in_use_cannot_be_deleted`）、Task 4（`test_removed_from_group_loses_access`）、Task 12（`test_delete_department_with_tickets_refused`）。

### Task 4: 访问规则 `access.py`（安全核心）

**Files:**
- Create: `aa_ticket/access.py`, `aa_ticket/tests/test_access.py`

**Interfaces:**
- Consumes: Task 2/3 的模型
- Produces（spec §6.2/§6.3，所有视图、服务、通知、统计只能用这些）：
  - `staff_department_ids(user) -> set[int]`：用户的组所绑定的、启用中的部门 id（每个请求缓存在 `user` 对象上）
  - `controller_department_ids(ticket) -> set[int]`：负责部门加它的所有祖先部门
  - `collaborator_department_ids(ticket) -> set[int]`：协作部门加它们的所有祖先部门
  - `is_controller(user, ticket) -> bool`：满足任一即可——属于 controller 部门、有 `view_all`、是当前处理人（处理人不能是提交人）
  - `is_collaborator(user, ticket) -> bool`
  - `is_staff_for(user, ticket) -> bool`：`(is_controller or is_collaborator) and user != ticket.requester`
  - `can_view(user, ticket) -> bool`：`user == requester or is_staff_for`
  - `can_view_internal(user, ticket) -> bool`：等于 `is_staff_for`，所以提交人永远是 False
  - `can_act(user, ticket, action: str) -> bool`，action 取以下值：
    - `"reply"`：提交人或 staff
    - `"note"`：staff
    - `"claim"`：controller 且非提交人，状态为 open
    - `"assign"`、`"invite"`、`"transfer"`、`"priority"`、`"category"`：controller
    - `"escalate"`：提交人，且 `next_escalation_target(ticket)` 不为 None，状态不是 closed
    - `"close"`：提交人或 controller，状态不是 closed
    - `"reopen"`：两种情况——controller（任何时候）；提交人，在 `closed_at + reopen_days` 之内
  - `visible_tickets(user) -> QuerySet[Ticket]`：用一条 SQL 实现 `can_view` 的逻辑，不能在 Python 里逐条过滤
  - `assignable_users(ticket) -> QuerySet[User]`：controller 部门组里的用户，排除提交人
  - `submittable_departments(user) -> QuerySet[Department]`：需要 `is_active`、`accepts_submissions`，并且满足以下任一条件：
    - submit_states 和 submit_groups 都为空
    - `user.profile.state` 在 submit_states 中
    - 用户的组和 submit_groups 有交集
  - `next_escalation_target(ticket) -> Department | None`：沿负责部门的祖先往上找，返回第一个在当前 `escalation_cycle` 里还没申请过的部门
  - `stats_department_ids(user) -> set[int] | None`：有 `view_all` 时返回 None（表示全部），否则返回自己部门加所有下级部门
